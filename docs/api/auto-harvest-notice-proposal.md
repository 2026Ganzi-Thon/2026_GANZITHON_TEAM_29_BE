# 자동 수확 알림 조회 계약 제안

상태: **결정 대기**. B의 `harvests` 스키마와 사용자 소유권·ack 계약이 병합되기 전에는 구현하거나 `get_my_farm()` 반환 타입을 변경하지 않습니다.

## 비교

| 기준 | A. `get_my_farm()` 객체 반환 | B. 별도 알림 조회 API |
|---|---|---|
| 형태 | `{ plots: [...], unacknowledged_auto_harvest_ids: [...] }` | 기존 밭 배열 + 별도 사용자 알림 응답 |
| 프론트 호환성 | 기존 배열 소비 코드를 모두 변경하는 breaking change | 기존 농장 렌더링 유지; 알림 호출만 추가 |
| 응답 중복 | 사용자 전체 ID를 한 번만 담을 수 있음 | 사용자 전체 ID를 한 번만 담음 |
| 밭 0개 | 객체 응답이므로 알림 조회 가능 | 농장과 무관하게 알림 조회 가능 |
| 데이터 일관성 | 한 DB 함수 스냅샷에서 함께 조회 가능 | 두 호출 사이 상태가 바뀔 수 있으나 ack 멱등성으로 처리 가능 |
| 마이그레이션 안전성 | 기존 함수 반환 타입 변경과 프론트 동시 배포 필요 | 새 함수 추가로 점진 배포 가능 |
| 사용자 격리 | 함수 내부 필터와 `harvests` RLS 필요 | 별도 함수 내부 필터와 `harvests` RLS 필요 |
| 유지보수성 | 농장 조회가 알림 수명주기에 결합 | 밭 투영과 알림/ack 책임이 분리됨 |

## 권장안

**B안: 기존 `get_my_farm()` 배열 계약을 유지하고 자동 수확 알림은 별도 조회 API로 분리**합니다.

이유:

- PR #7과 프론트의 밭 배열 계약을 깨지 않음
- 밭이 0개여도 사용자 알림을 조회할 수 있음
- B의 `ack_auto_harvest_notice(p_harvest_ids)`와 같은 수명주기로 관리 가능
- `harvests` 도입 이후 새 마이그레이션으로 안전하게 추가 가능
- 사용자 전체 알림 ID를 각 밭 행에 중복하지 않음

별도 조회 함수명, 반환 필드, 정렬, 페이지 크기와 알림 생성 기준은 A/B/프론트엔드 합의 후 확정합니다. 두 호출 사이의 경합은 ack RPC가 본인 미확인 알림만 멱등 처리하는 계약으로 해결하고, 필요 시 조회 응답에 서버 시각을 포함하는 방안을 검토합니다.

## 구현 선행 조건

- `harvests.id`, `harvests.user_id` 또는 소유권 JOIN 경로
- 자동/수동 수확 구분 필드
- 알림 확인 시각 또는 별도 ack 테이블
- 세션당 수확 1회 UNIQUE
- authenticated 전용 실행 권한과 사용자별 RLS
- 다른 사용자 ID 차단, 중복 ack, 빈 결과 테스트
